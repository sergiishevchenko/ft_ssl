# Принцип работы ft_ssl

`ft_ssl` считает хеш MD5, SHA-256 или Whirlpool и печатает его в формате задания. Библиотечных функций хеширования нет: алгоритмы лежат в `srcs/md5`, `srcs/sha256` и `srcs/whirlpool`. Разбор командной строки, чтение данных и формат печати общие для всех трёх команд.

## Кто кого вызывает

```text
main
 ├─ нет аргументов → print_usage → interactive_mode
 │                                    ├─ read_line
 │                                    ├─ split_line / get_next_word
 │                                    └─ find_hash → execute_command
 └─ есть argv[1] → find_hash
                   ├─ не найдено → print_invalid_command, код 1
                   └─ найдено → execute_command
                                  ├─ parse_flags
                                  ├─ process_stdin   ─┐
                                  ├─ process_string  ─┼─ hash_data → init/update/final
                                  └─ process_file    ─┘
                                         └─ print_hash_result
```

`find_hash` не содержит отдельной ветки `if (md5) / if (sha256)`. Имя сравнивается с полем `name_lower` в массиве `g_hashes`. В той же записи лежат указатели на `init`, `update` и `final` конкретного алгоритма.

## Два входа

### Команда в аргументах

```text
./ft_ssl md5 -r -p -s "foo" file
 argv[0]  argv[1]  argv[2] ...
```

`argc` здесь больше 1. `main` вызывает `find_hash(argv[1])`. При успехе заполняется структура `t_ssl`:

| Поле | Значение в этом запуске |
|---|---|
| `hash` | запись MD5 из `g_hashes` |
| `argc`, `argv` | командная строка целиком |
| `cmd_index` | `2`, потому что флаги начинаются с `argv[2]` |
| `flags` | обнуляются уже внутри `execute_command` |

### Нет аргументов

`argc < 2`. Сначала `print_usage` пишет в stderr:

```text
usage: ft_ssl command [flags] [file/string]
```

Потом `interactive_mode`. Перед каждой строкой печатается `ft_ssl> ` без перевода строки. Строка читается из stdin до `\n` или до конца ввода. Пустая строка ничего не делает. Первое слово — команда, остальные слова проходят через тот же `execute_command`. Отличие одно: в собранном `argv` нет имени программы, поэтому `cmd_index` равен `1`, а не `2`.

`Ctrl+D` на пустой строке даёт конец ввода. `read_line` возвращает `NULL`, цикл завершается, программа выходит с кодом 0.

Строка длиннее 127 байт в текущем `read_line` собирается неправильно: при расширении буфера уже прочитанные байты освобождаются и в новый буфер не копируются. Короткие команды из задания укладываются в первый буфер.

Кавычки в интерактиве снимаются. Строка

```text
md5 -s "hello world"
```

даёт три слова: `md5`, `-s`, `hello world`.

Неизвестная команда в интерактиве печатает только `ft_ssl: Error: '<имя>' is an invalid command.` и не завершает программу. Следующее приглашение всё равно появится.

## Разбор флагов

`parse_flags` идёт слева направо, пока аргумент похож на флаг.

| Аргумент | Куда попадает |
|---|---|
| `-p` | `ssl->flags.p = 1` |
| `-q` | `ssl->flags.q = 1` |
| `-r` | `ssl->flags.r = 1` |
| `-s` и следующий аргумент | текст копируется указателем в массив `strings`, счётчик `str_count` растёт, оба аргумента пропускаются |
| что угодно другое | цикл останавливается, индекс остаётся на этом аргументе |

Повторный `-q` просто ещё раз записывает 1. Порядок `-p -q -r -s` среди флагов не важен. Важен момент, когда встретился первый не-флаг: всё после него, включая новое `-s` и `-p`, уже имена файлов.

Строки `-s` не хешируются сразу. Они складываются в массив, потому что при `-p` stdin должен быть напечатан раньше строк. Лимит массива — 256 строк.

Если `-s` стоит последним и после него нет текста, флаг никуда не девается и строка не создаётся.

### Пример из задания по шагам

Команда:

```text
echo "one more thing" | ./ft_ssl md5 -r -p -s "foo" file -s "bar"
```

Аргументы после имени команды:

| Индекс | Текст | Как понят |
|---|---|---|
| 2 | `-r` | флаг `r` |
| 3 | `-p` | флаг `p` |
| 4 | `-s` | начало строки |
| 5 | `foo` | отложенная строка |
| 6 | `file` | не флаг, разбор флагов кончается |
| 7 | `-s` | имя файла |
| 8 | `bar` | имя файла |

Дальше `execute_command` делает четыре дела строго в этом порядке:

1. `flags.p` включён, поэтому `process_stdin` читает пайп. В нём байты `one more thing\n`.
2. Печатает хеш отложенной строки `foo`.
3. Открывает файл `file`.
4. Пытается открыть файлы `-s` и `bar`. Обоих нет, на каждый пишется ошибка в stderr, программа идёт дальше и всё равно возвращает 0.

Вывод совпадает с заданием:

```text
one more thing
("one more thing")= a0bd1876c6f011dd50fae52827f445f5
acbd18db4cc2f85cedef654fccc4a4d8 "foo"
53d53ea94217b259c11a5a2d104ec58a file
ft_ssl: md5: -s: No such file or directory
ft_ssl: md5: bar: No such file or directory
```

Первая строка — сырой stdin из-за `-p`. Вторая — тот же текст без завершающего `\n`, в кавычках, и его хеш. Кавычки вокруг `foo` появляются из-за `-r` и того, что это строка, а не файл. У файла `file` кавычек нет. `-r` ставит хеш слева.

### Когда stdin читается сам

Если после разбора не было ни `-p`, ни одной строки, ни одного файла, `execute_command` вызывает `process_stdin` сам. Это команда `echo "42 is nice" | ./ft_ssl md5`. Флага `-p` нет, поэтому содержимое не повторяется, а печатается `(stdin)= <хеш>`.

Если файл есть, а `-p` нет, stdin не читается. Пайп в `echo "..." | ./ft_ssl md5 file` программа игнорирует и хеширует только файл.

## Как печатается результат

Есть два пути.

`print_hash_result` обслуживает строку (`is_file == 0`) и файл (`is_file == 1`). `label` — это сам текст или имя файла. `hex` — уже готовая строка из символов `0-9a-f`.

Решение идёт сверху вниз, срабатывает первая подходящая ветка:

1. `flags.q` — в stdout только `hex` и перевод строки. `-r` в этой ветке уже не смотрится.
2. `flags.r` — `hex`, пробел, затем цель. Строка в кавычках, имя файла без кавычек.
3. Иначе `NAME ("label") = hex` или `NAME (label) = hex`. `NAME` — поле `name_upper`: `MD5`, `SHA256` или `WHIRLPOOL`.

`process_stdin` эту функцию не вызывает, у него свой формат:

| Флаги | Что происходит с байтами stdin |
|---|---|
| `-p` | байты сразу пишутся в stdout, включая последний `\n`, если он был |
| `-p` и не `-q` | затем `("содержимое")= hex`. Последний `\n` внутрь кавычек не входит |
| `-q` | одна строка `hex`. Если вместе с `-p`, сырой текст уже напечатан выше |
| `-r`, но не `-q` и не `-p` | `hex *stdin` |
| ничего из этого | `(stdin)= hex` |

Ошибка файла пишется в stderr и не смешивается с хешем:

```text
ft_ssl: md5: имя: No such file or directory
```

`md5` здесь — `name_lower` выбранной команды. После ошибки остальные цели всё равно обрабатываются.

## Как байты становятся хешем

`process_stdin`, `process_string` и `process_file` в конце вызывают одну функцию `hash_data`.

```text
контекст на стеке, 256 байт
        │
        ▼
     init(ctx)          начальное состояние, счётчик = 0, хвост пуст
        │
        ▼
     update(ctx, data, len)
        │  каждый байт кладётся в ctx->buffer
        │  когда buflen становится 64, блок сжимается и buflen снова 0
        ▼
     final(digest, ctx)
        │  байт 0x80, нули, длина сообщения в битах
        │  последний блок сжимается
        ▼
     digest_to_hex
        каждый байт дайджеста → два символа hex
```

`data` может быть `NULL`, только если `len == 0`. Так бывает на пустом stdin: цикл `update` ни разу не читает указатель, а `final` считает хеш пустого сообщения.

Длина дайджеста берётся не из алгоритма в момент печати, а из поля `digest_size` записи команды: 16, 32 или 64. Буфер `digest[64]` рассчитан на самый большой из них. В hex попадают только первые `digest_size` байт.

### Хвост и паддинг

Сообщение почти никогда не кратно 64 байтам. Неполный кусок лежит в `buffer`, его длина — `buflen`. `final` дописывает:

1. Байт `0x80` (бит 1 и семь нулевых бит).
2. Нулевые байты.
3. Длину исходного сообщения в битах, то есть `count * 8`.

Куда ставится длина:

| Алгоритм | Сколько байт под длину | Порядок байт | Куда в блоке |
|---|---|---|---|
| MD5 | 8 | младший байт первым | байты 56–63 |
| SHA-256 | 8 | старший байт первым | байты 56–63 |
| Whirlpool | 32, из них старшие 24 нули | старший байт 64-битной длины первым | байты 32–63, сама длина в 56–63 |

Если `0x80` и нули не помещаются до поля длины, текущий блок добивается нулями до 64, сжимается, и длина записывается уже в следующий блок. Пустое сообщение поэтому занимает один блок: `80`, потом нули, потом нулевая длина.

`count` увеличивается на число байт, которые реально пришли в `update`. Паддинг в `count` не входит.

### Сжатие блока

У всех трёх функций блок 64 байта превращается в слова, слова прогоняются через раунды, результат прибавляется или ксорится к состоянию. Состояние после последнего блока и есть дайджест.

MD5 собирает 16 слов little-endian и крутит четыре регистра 64 раза. В конце рабочие регистры прибавляются к `state`.

SHA-256 собирает 16 слов big-endian, расширяет их до 64 и 64 раза обновляет восемь рабочих слов. В конце они прибавляются к `state`.

Whirlpool собирает 8 слов big-endian. Десять раундов шифра W обновляют ключ и блок. Ключ в начале равен старому состоянию. После раундов состояние ксорится с результатом шифра и с исходным блоком. Это схема Miyaguchi–Preneel, не сложение, как у MD5 и SHA-256.

## MD5 по шагам

Начальное состояние, четыре слова:

```text
A = 0x67452301
B = 0xefcdab89
C = 0x98badcfe
D = 0x10325476
```

Блок из 64 байт режется на `m[0]…m[15]`. Байт 0 блока — младший байт `m[0]`.

64 шага делятся на четыре раунда. На шаге `j` берутся текущие `a b c d`:

```text
F = нелинейная функция этого раунда от b, c, d
g = номер слова сообщения
a, b, c, d ← d, b + rotate_left(a + F + T[j] + m[g], s[j]), b, c
```

Функции по раундам:

| Шаги | Функция | Индекс слова |
|---|---|---|
| 0–15 | `(b & c) \| (~b & d)` | `j` |
| 16–31 | `(d & b) \| (~d & c)` | `(5j + 1) mod 16` |
| 32–47 | `b ^ c ^ d` | `(3j + 5) mod 16` |
| 48–63 | `c ^ (b \| ~d)` | `(7j) mod 16` |

`T[j]` — таблица `g_t`, целая часть `2^32 * |sin(j+1)|`. `s[j]` — таблица `g_s`, величина циклического сдвига. Сложение 32-битное: переполнение обрезается.

После 64 шагов `state[0] += a` и так же для B, C, D. Следующий блок стартует уже с этого нового состояния.

В дайджест слова выгружаются little-endian: сначала младший байт A, затем остальные байты A, потом B, C и D. Получается 16 байт, 32 hex-символа.

## SHA-256 по шагам

Восемь начальных слов `H0…H7` — это первые 32 бита дробных частей квадратных корней первых восьми простых чисел. Они записаны в `sha256_init`.

Блок читается как 16 слов big-endian: байт 0 — старший байт `w[0]`. Дальше слова до 63:

```text
σ0(x) = rotr(x, 7) ^ rotr(x, 18) ^ (x >> 3)
σ1(x) = rotr(x, 17) ^ rotr(x, 19) ^ (x >> 10)
w[i] = w[i-16] + σ0(w[i-15]) + w[i-7] + σ1(w[i-2])
```

`>>` здесь логический сдвиг, биты не заворачиваются. `rotr` заворачивает.

Рабочие слова `a…h` копируются из состояния. Раунд `i`:

```text
Σ1(e) = rotr(e, 6) ^ rotr(e, 11) ^ rotr(e, 25)
Ch(e,f,g) = (e & f) ^ (~e & g)
T1 = h + Σ1(e) + Ch(e,f,g) + K[i] + w[i]

Σ0(a) = rotr(a, 2) ^ rotr(a, 13) ^ rotr(a, 22)
Maj(a,b,c) = (a & b) ^ (a & c) ^ (b & c)
T2 = Σ0(a) + Maj(a,b,c)

h,g,f,e,d,c,b,a ← g, f, e, d+T1, c, b, a, T1+T2
```

`K[i]` — таблица `g_k`, дробные части кубических корней первых 64 простых чисел.

После 64 раундов каждое рабочее слово прибавляется к соответствующему `state[i]`. В дайджест восемь слов пишутся big-endian: 32 байта, 64 hex-символа.

## Whirlpool по шагам

Состояние — восемь 64-битных слов. `whirlpool_init` обнуляет весь контекст, отдельных стартовых констант нет.

Блок из 64 байт становится словами `blk[0]…blk[7]`, старший байт слова идёт первым. Ключ раунда `k` в начале копирует текущее состояние. Шифруемый блок `s` — это `blk[i] ^ k[i]`.

Дальше 10 раундов. Один раунд для восьми слов делает `wp_round`:

- из слова `(row - t) mod 8` берётся байт номер `t`;
- этот байт — индекс в таблице `g_whirlpool_c0`;
- значение таблицы для `t > 0` циклически сдвигается на `t` байт вправо;
- восемь таких значений ксорятся.

`C0` уже содержит подстановку S-box и умножение на первую строку матрицы MDS. Сдвиг байт внутри 64-битного слова заменяет отдельные таблицы `C1…C7`.

После раунда ключа в `nk[0]` ксорится `g_whirlpool_rc[r]`. Константа раунда `r` собрана из восьми значений S-box: байты `8*r … 8*r+7`.

Затем тот же `wp_round` применяется к состоянию шифра, и результат ксорится с новым ключом.

Когда десять раундов кончились:

```text
state[i] ^= s[i] ^ blk[i]
```

`s` здесь — выход шифра, `blk` — исходный блок. Старое состояние уже сидит внутри ключа, с которого шифр начинался, поэтому третий ксор с исходным состоянием отдельно не пишется.

Дайджест — 64 байта, 128 hex-символов, слова big-endian.

Паддинг отличается от MD5 тем, что поле длины занимает 32 байта. Пока сообщение короче `2^64` бит, байты 32–55 нулевые, а в байтах 56–63 лежит длина в битах старшим байтом вперёд. Если после `0x80` до байта 32 места нет, блок закрывается раньше и длина уходит в следующий блок.

## Память на один запуск

| Что | Где живёт | Когда освобождается |
|---|---|---|
| `t_ssl`, флаги | стек `main` или `exec_interactive_line` | вместе с функцией |
| контекст хеша, 256 байт | стек `hash_data` | вместе с функцией |
| дайджест и hex-строка | стек `process_*` | вместе с функцией |
| байты stdin или файла | куча, `read_fd` | `free` в конце `process_stdin` / `process_file` |
| строка интерактива | куча, `read_line` | `free` в цикле `interactive_mode` |
| слова интерактива | куча, `get_next_word` и `split_line` | `free_argv` после `execute_command` |

`read_fd` читает порциями по 4096 байт (`BUF_SIZE`) и каждый раз выделяет новый буфер ровно под уже прочитанное плюс новую порцию. Старый буфер копируется и освобождается. Файл целиком оказывается в одном блоке до вызова `hash_data`.

Отдельного `malloc` под контекст нет. `ctx_size` в таблице команд записан, но `hash_data` им не пользуется: буфер фиксированный и больше любого из трёх контекстов.

`ft_strdup` и `get_hash_count` в работе программы не участвуют. `ft_putnbr_hex` объявлен в заголовке и нигде не определён.

## Ошибки, которые программа не роняют

- Неизвестная команда в `argv[1]` печатает список команд и флагов и выходит с кодом 1.
- Неизвестный файл печатает строку в stderr. Код возврата остаётся 0, если до этого не было другой причины выйти.
- Пустой stdin хешируется как пустое сообщение.
- `free(NULL)` после пустого чтения допустим.

`read_fd` при неудачном `malloc` освобождает уже накопленное и возвращает `NULL`. Длину в этом случае он не записывает. Обычный запуск на заданных примерах до этой ветки не доходит.

## Что нужно, чтобы добавить команду

Новая функция хеша обязана принять те же три указателя, что стоят в `t_hash_func`: `init(void *)`, `update(void *, data, len)`, `final(digest, void *)`. Внутри `void *` приводится к своему контексту.

В `g_hashes` добавляется одна строка до завершающего `{NULL, ...}`: подпись для вывода, имя команды, размер дайджеста в байтах, размер контекста, три функции. `main`, разбор флагов и печать не меняются. `find_hash` подхватит новое имя, `print_invalid_command` само напечатает его в списке команд.
