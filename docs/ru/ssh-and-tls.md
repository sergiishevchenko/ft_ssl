# SSH и TLS

`ft_ssl` назван в честь OpenSSL, но считает только хеш: MD5, SHA-256 и Whirlpool. Канала, ключей и сертификатов в программе нет.

SSH и TLS — протоколы поверх TCP. Оба закрывают соединение: собеседник подтверждается, байты шифруются, подмена по дороге обнаруживается. Хеш там есть, но он один из кусков, не весь протокол.

## Хеш, шифр и подпись

Три разные задачи. Путать их на защите — обычная ошибка.

| | Хеш | Шифр | Подпись или MAC |
|---|---|---|---|
| Задача | отпечаток сообщения | скрыть текст | доказать, кто это сделал, и что байты не меняли |
| Ключ | нет | есть | есть |
| Обратимость | нет | да, тем же или парным ключом | подпись проверяется, исходный текст из неё не читается |
| Пример | SHA-256 от файла | AES, ChaCha20 | RSA, ECDSA, Ed25519, HMAC |
| Что делает `ft_ssl` | да | нет | нет |

Одинаковый вход всегда даёт одинаковый SHA-256. Ключа нет, поэтому это не шифрование пароля и не «закрытый» файл.

MAC — хеш с ключом. Обычный SHA-256 файла может пересчитать кто угодно. HMAC-SHA-256 без секретного ключа не сойдётся, поэтому им проверяют, что пакет пришёл от того, с кем только что договорились о ключе.

Подпись — то же доказательство, но ключи разные. Закрытым подписывают, открытым проверяют. В подпись обычно идёт не само сообщение, а его хеш.

## TLS

TLS защищает поток байтов между клиентом и сервером. Поверх него живут другие протоколы: HTTPS — это HTTP внутри TLS, порт 443. Так же устроены защищённые SMTP, IMAP и много служебных API.

SSL — прежнее имя той же идеи. SSLv2 и SSLv3 сломаны и в живых клиентах выключены. Сейчас остаются TLS 1.2 и TLS 1.3. Слово SSL в названии OpenSSL и в `ft_ssl` историческое.

TLS даёт три вещи сразу:

- сервер подтверждён сертификатом, а не только адресом в строке браузера;
- прикладные байты шифруются;
- приписанный по дороге байт ломает проверку целостности, и запись отбрасывается.

Клиентский сертификат возможен, но у обычного сайта его нет. Браузер логинит пользователя уже внутри HTTPS, паролем или cookie, а не сертификатом TLS.

### Рукопожатие

До прикладных данных стороны выбирают алгоритмы и получают общие симметричные ключи. Асимметрия нужна только здесь: ей проверяют сертификат и обмениваются секретом. Дальше идёт быстрый шифр.

Упрощённый TLS 1.3:

```text
клиент                         сервер
  |  ClientHello                 |
  |  (набор шифров, key_share)   |
  | -------------------------->  |
  |               ServerHello    |
  |               Certificate    |
  |               CertificateVerify
  |               Finished       |
  | <--------------------------  |
  |  Finished                    |
  | -------------------------->  |
  |  HTTP и прочие данные, уже   |
  |  под симметричным ключом     |
```

`key_share` — открытая половина эфемерного ключа Диффи–Хеллмана, обычно X25519. Общий секрет есть только у этих двух сторон и только на это соединение. Запись трафика потом бесполезна, даже если позже украдут долгоживущий ключ сертификата. Это и есть прямая секретность.

`Certificate` — цепочка X.509. Сервер показывает свой сертификат и сертификаты промежуточных центров. Клиент проверяет подпись по цепочке до корня, который уже лежит в системе или в браузере.

`CertificateVerify` — подпись сервера закрытым ключом сертификата. Подписывается не страница сайта, а хеш уже прошедших сообщений рукопожатия. Так ключ из сертификата привязывается к этому конкретному обмену.

`Finished` — проверка тем же хешем стенограммы, но уже через ключ, выведенный из общего секрета. Если кто-то подменил `ClientHello` по дороге, стороны это видят.

Имя шифра TLS 1.3 выглядит так: `TLS_AES_128_GCM_SHA256`. AES-GCM шифрует и одновременно ставит метку целостности. SHA-256 в хвосте имени — хеш для вывода ключей (HKDF), а не отдельный проход по данным пользователя.

В TLS 1.2 встречаются и старые наборы, где шифр и MAC разделены: AES-CBC плюс HMAC-SHA-256. Их вытесняют AEAD-наборы, GCM и ChaCha20-Poly1305.

### Где здесь хеш

| Место | Зачем |
|---|---|
| Подпись сертификата | центр сертификации подписывает хеш тела сертификата. Сейчас это SHA-256 с RSA или ECDSA |
| Стенограмма рукопожатия | один хеш всех сообщений обмена. Им питаются `CertificateVerify` и `Finished` |
| Вывод ключей | из общего секрета Диффи–Хеллмана получаются ключи записи. В TLS 1.3 это HKDF на SHA-256 или SHA-384 |
| Старый HMAC | в наборах TLS 1.2 без AEAD каждый фрагмент закрывается HMAC |

MD5 и SHA-1 в сертификатах больше не принимают: для них умеют строить коллизии, то есть два разных сертификата с одним хешем.

## SSH

SSH — удалённый вход на машину. Порт 22. Поверх того же транспорта работают команды, перенаправление портов, `scp` и `sftp`. Это не «TLS для терминала» и не надстройка над OpenSSL: отдельный протокол, SSH-2.

Три слоя, снизу вверх:

1. Транспорт. Обмен ключами, ключ сервера, шифр.
2. Аутентификация пользователя. Ключ или пароль.
3. Каналы. Сессия шелла, `exec`, туннель, SFTP.

### Транспорт

```text
клиент                         сервер
  |  версия протокола            |
  | <------------------------->  |
  |  списки алгоритмов (KEXINIT) |
  | <------------------------->  |
  |  Диффи–Хеллман               |
  | <------------------------->  |
  |  подпись H ключом хоста      |
  | <--------------------------  |
  |  NEWKEYS, дальше шифр        |
```

Стороны выбирают обмен (`curve25519-sha256` или старше — `diffie-hellman-group14-sha256`), тип ключа хоста (`ssh-ed25519`, `rsa-sha2-256`, `ecdsa-sha2-nistp256`) и шифр на данные (`chacha20-poly1305`, `aes256-gcm` или AES-CTR вместе с отдельным HMAC).

Общий секрет `K` сам по себе ещё не ключ сессии. Из него и из хеша обмена `H` выводятся ключи в обе стороны: отдельно на шифр клиента, шифр сервера и, если шифр не AEAD, на MAC. Первый `H` запоминается как идентификатор сессии и участвует во входе пользователя.

Сервер подписывает `H` своим закрытым ключом хоста. Клиент проверяет подпись открытым ключом. Подпись сходится только если это обладатель того самого ключа и обмен не изменили.

### Ключ хоста

У SSH нет обязательного центра сертификации. Клиент помнит ключ сервера сам. Это trust on first use: при первом соединении ключ показывается и записывается в `~/.ssh/known_hosts`. В следующий раз тот же адрес с другим ключом — ошибка, соединение рвётся. Так ловят подмену сервера, но только после первого, уже проверенного захода.

На экран выводится не весь ключ, а отпечаток. Современный OpenSSH показывает SHA-256 в Base64:

```text
SHA256:abcdefghijklmnopqrstuvwxyz0123456789ABCD
```

Старый формат — MD5 побайтно через двоеточие. Это тот же приём, что и хеш файла: длинный ключ сверяют по короткому отпечатку. Для отпечатка коллизия MD5 уже не подходит, поэтому живой формат — SHA-256.

### Вход пользователя

К этому моменту канал уже зашифрован. Сервер ещё не знает, кто клиент.

Обычный способ — ключ. Открытая половина лежит на сервере в `~/.ssh/authorized_keys`. Клиент подписывает идентификатор сессии и запрос на вход своим закрытым ключом. Закрытый ключ по сети не уходит.

Пароль тоже возможен: он едет внутри уже поднятого шифра. На сервере его сверяют с локальной учётной записью. Хеш в `/etc/shadow` — это не MD5 и не SHA-256 из `ft_ssl`, а отдельная функция паролей (`yescrypt`, `bcrypt` и похожие), с солью и намеренно медленная.

Неизвестный ключ или неверный пароль не ломают транспорт. Можно пробовать следующий способ, пока сервер не закроет попытки.

## Чем они отличаются

| | TLS | SSH |
|---|---|---|
| Задача | защитить прикладной поток, чаще всего HTTP | удалённая команда, файл, туннель |
| Порт по умолчанию | 443 | 22 |
| Кто такой сервер | сертификат, подписанный центром | ключ хоста, запомненный клиентом |
| Кто такой клиент | обычно никак, иногда свой сертификат | ключ пользователя или пароль |
| Где лежит доверие | хранилище корней в ОС или браузере | `known_hosts` и `authorized_keys` |
| Хеш обмена | стенограмма рукопожатия, HKDF | хеш `H`, из него ключи сессии |
| Шифр данных | AES-GCM, ChaCha20-Poly1305 | те же классы, свои имена алгоритмов |
| Библиотека | OpenSSL, LibreSSL, BoringSSL и другие | обычно свой код демона `sshd`, не OpenSSL |

Общее устройство одно. Сначала асимметричный обмен и подпись, хеш связывает сообщения обмена в одно значение, потом обе стороны считают симметричные ключи и говорят уже ими. Ни там, ни там хеш не заменяет шифр: SHA-256 файла не прячет файл.

## Алгоритмы этого проекта

| Команда `ft_ssl` | В SSH и TLS |
|---|---|
| `sha256` | рабочий хеш. Отпечатки OpenSSH, подписи сертификатов, HKDF в TLS 1.3, обмен `curve25519-sha256`, HMAC-SHA-256 в старых наборах |
| `md5` | в протоколах больше не используется. Коллизии находятся намеренно, поэтому им нельзя подписывать сертификат. Как контрольная сумма файла ещё встречается, на безопасность канала не годится |
| `whirlpool` | в SSH и TLS нет. Это отдельный хеш ISO, в проекте он бонус |

`sha256` в имени шифра или обмена не значит, что данные пользователя прогоняются через SHA-256. Так называют хеш, которым мешают секрет и стенограмму, прежде чем получить ключ шифра.

## Чего в программе нет

- сокетов, порта 22 и порта 443;
- Диффи–Хеллмана и любых ключей;
- сертификатов X.509 и `known_hosts`;
- AES, ChaCha20, HMAC;
- подписи RSA, ECDSA, Ed25519.

`./ft_ssl sha256 -s "hello"` печатает хеш строки. Тот же примитив стоит внутри SSH и TLS, но соединение из этого вызова не получается.
